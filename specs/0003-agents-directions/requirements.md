# 0003 Agentes y direcciones visuales reference-only — Requirements

## Context

Parte P3 del master-plan `01-heron` (`specs/_master/01-heron/MASTER.md` › P3, `parts.json` › P3): Heron usa Claude Code y Codex CLI ya autenticados (D18) como motores de razonamiento detrás del puerto `AgentProvider` para formular el research por trabajo de interfaz (`research brief`), interpretar referencias (`research analyze`) y proponer 3 direcciones visuales exploratorias con los datos de su propuesta visual (`direction propose`, D23), y para registrar una dirección preferida sin aprobar nada (`direction select`, D12). El agente nunca escribe, nunca ejecuta herramientas y nunca ve secretos: devuelve JSON atado a un schema que Heron revalida y escribe. Al cerrar, el modo `reference-only` de §76 queda completo sobre un repo real.

Decisiones aplicables: D10, D12, D14, D16, D18, D23, D24, D26; reglas RN-5, RN-13, RN-16, RN-33, RN-34, RN-35, RN-36, RN-40, RN-41; RNF-5, RNF-6, RNF-7, RNF-8, RNF-12, RNF-14, RNF-15, RNF-19, RNF-20. Las decisiones del usuario del 2026-10-01 están en `design.md` como DR35–DR38 (autenticación y términos, modelo, análisis solo con texto, sin tope duro de costo). R19–R21 cubren su requisito de economía de tokens. Se integra después de `specs/0004-product-context` y de su micro-tarea compartida (`design.md` DR31).

## Requirements (EARS)

**Frontera de invocación**

- **R1** — CUANDO Heron invoque un agente CLI, el sistema DEBERÁ lanzarlo como proceso hijo con `cwd` en un directorio temporal vacío creado por Heron y nunca con `--bare`; para Claude Code DEBERÁ pasar `-p`, `--tools ""`, `--strict-mcp-config`, `--output-format json`, `--json-schema` y `--no-session-persistence`, y para Codex CLI `exec --sandbox read-only --ephemeral --skip-git-repo-check --output-schema`, más las banderas de aislamiento de `design.md` (DR6 y §Contracts › 7); SI la versión instalada no lista alguna de esas banderas ENTONCES DEBERÁ negarse a invocar (`AGENT_UNAVAILABLE`, exit 5). Criterios: P3.A1.
- **R2** — El sistema DEBERÁ construir el entorno del proceso hijo por lista blanca, de modo que nunca contenga variables `HERON_*` ni `PENPOT_*`; por DR35 tampoco DEBERÁ contener credenciales de API (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`, `CODEX_API_KEY`) ni variables de ruta de nube (`CLAUDE_CODE_USE_BEDROCK|VERTEX|FOUNDRY`, `ANTHROPIC_BASE_URL`), y CUANDO alguna esté definida en el entorno de Heron DEBERÁ informarlo con `AGENT_ENV_IGNORED`. Criterios: P3.A5.
- **R3** — SI la salida de un agente no cumple el schema de la tarea o falla un validador determinista de la tarea ENTONCES el sistema DEBERÁ reintentar con una invocación de reparación como máximo 2 veces y, si sigue inválida, terminar el run como `invalid-output` con exit 4, sin cambiar `state.json` ni escribir artefactos. Criterios: P3.A2.
- **R4** — CUANDO una invocación supere el timeout configurado (`agents.timeoutMs`, entre 1 000 y 3 600 000 ms, 600 000 por default, RNF-6), el sistema DEBERÁ enviar SIGTERM al grupo de procesos del hijo, SIGKILL a lo sumo 5 s después, dejar de esperar su salida en un tiempo acotado y terminar el run como `timeout` con exit 5 sin escribir artefactos. Criterios: P3.A3.
- **R5** — CUANDO el sistema construya el context pack de una tarea, DEBERÁ incluir solo los tipos de ítem que la tarea declara, proyectar cada referencia por lista blanca de campos, delimitar como dato todo ítem que no sea de Heron y marcar `untrusted` el contenido externo y toda salida previa de un agente, y respetar el presupuesto de caracteres (120 000 por default, RNF-12) con un recorte determinista que emite `CONTEXT_PACK_TRIMMED`; SI aun recortado excede el presupuesto ENTONCES DEBERÁ salir con exit 2 (`CONTEXT_PACK_OVER_BUDGET`) sin invocar al agente. Criterios: P3.A4.
- **R6** — CUANDO un run de agente termine con éxito, el sistema DEBERÁ escribir en la misma transacción que sus salidas un `AgentRun` en `.heron/runs/<runId>.json` con proveedor, rol, modelo (pedido y reportado), versión de CLI, plantilla `<persona>/<tarea>@v<n>` con su sha256, sha256 y dialecto del schema de salida, hashes de entrada (pack y artefactos) y de salida, duración y costo cuando el proveedor lo reporta (RN-41); ningún valor secreto cargado DEBERÁ aparecer en el `AgentRun`, en los logs, en el envelope ni en `.heron/`. Criterios: P3.A5.
- **R7** — El sistema DEBERÁ resolver el proveedor de cada rol (`creator`, `reviewer`) solo desde la configuración (`project.json` › `agents.roles`, default `creator = claude-code`, `reviewer = codex-cli`), de modo que intercambiar los roles no requiera cambiar código; SI `agents` no cumple su schema ENTONCES los comandos de agente DEBERÁN salir con exit 2 (`AGENT_CONFIG_INVALID`) y los demás comandos NO DEBERÁN verse afectados. Criterios: P3.A6.
- **R8** — MIENTRAS un agente Codex esté en ejecución, el sistema DEBERÁ leer su flujo de eventos `--json` y, SI aparece un evento o un ítem fuera de la lista blanca (solo mensajes y razonamiento del agente) o una línea no reconocible ENTONCES DEBERÁ detener el proceso y terminar el run como `policy-violation` con exit 3, sin escribir artefactos y sin exponer el contenido de esa línea en findings, logs ni resultados. Criterios: P3.A1.

**Research con agentes**

- **R9** — CUANDO el usuario ejecute `heron research brief`, el sistema DEBERÁ obtener del rol `creator` consultas de research donde cada una nombra una faceta de §8 y el trabajo de la interfaz que estudia, y persistirlas en `.heron/research/brief.json` con origen `inferred` junto a las consultas del usuario (`provided`), que se conservan entre corridas salvo `--reset-queries`; SI una consulta del usuario (`--query <faceta>:<texto>`) o del agente carece de faceta o solo contiene términos genéricos (p. ej. "beautiful UI") ENTONCES DEBERÁ rechazarla (`RESEARCH_QUERY_INVALID`, exit 2 si viene del usuario; reparación si viene del agente). Criterios: P3.A8, P3.A12.
- **R10** — CUANDO el usuario ejecute `heron research analyze`, el sistema DEBERÁ obtener del rol `creator` notas por referencia y persistirlas en `.heron/research/analysis.json` con origen `inferred`, atadas al hash de la referencia analizada, sin modificar `references.json`, `provenance.json` ni ningún campo humano. Criterios: P3.A12.

**Direcciones visuales**

- **R11** — CUANDO el usuario ejecute `heron direction propose` desde `research-ready` o `directions-ready` con la aprobación del gate `research` vigente, el sistema DEBERÁ obtener del rol `creator` exactamente 3 direcciones (`DIR-A`..`DIR-C`) con los 13 atributos de §11, cada una citando ≥ 2 referencias activas existentes con qué toma y qué no copiar, persistirlas en `.heron/research/visual-directions.json` marcadas `reference-only` y avanzar a `directions-ready`; SI la aprobación de `research` no está vigente ENTONCES DEBERÁ salir con exit 3 antes de invocar al agente. Criterios: P3.A7.
- **R12** — Cada dirección DEBERÁ traer su propuesta visual completa (paleta provisional con pares texto/fondo, escala tipográfica, hoja de componentes básicos y una composición genérica marcada `SYNTHETIC`), y el sistema DEBERÁ calcular de forma determinista el contraste WCAG de cada par (nunca tomar el del agente) y rechazar una propuesta incompleta o con un par bajo su umbral de RNF-9. Criterios: P3.A10.
- **R13** — CUANDO el usuario ejecute `heron direction select <DIR-x>`, el sistema DEBERÁ registrar la dirección como `preferred` con identidad y fecha mientras las direcciones sean `reference-only` (D12), sin transición de fase; el estado NUNCA DEBERÁ llegar a `direction-selected` por este comando. Criterios: P3.A7.

**Operación**

- **R14** — CUANDO el usuario ejecute `heron doctor`, el sistema DEBERÁ reportar por cada proveedor asignado a un rol su disponibilidad, su versión frente a la mínima y su sesión usando solo `--version` y el exit code de `claude auth status` / `codex login status`, sin leer archivos de credenciales y sin que un agente ausente cambie el exit code; CUANDO pase `--deep`, DEBERÁ además ejecutar por proveedor una sonda real atada a schema con su propio timeout, y una sonda fallida DEBERÁ dar exit 5. Criterios: P3.A9.
- **R15** — El sistema DEBERÁ registrar cada invocación de agente como evento `agent.invocation` en `.heron/logs/<YYYY-MM-DD>.jsonl` (append-only, ignorado por Git) con `runId`, duración y resultado, redactando por clave y por valor cargado, y DEBERÁ podar los archivos de log con más de 30 días (D16). Criterios: P3.A5.
- **R16** — CUANDO existan `brief.json`, `analysis.json` o `visual-directions.json`, `REFERENCES.md` DEBERÁ mostrarlos en secciones propias que marquen el origen `inferred`, `reference-only` y `SYNTHETIC`, con todo texto del agente escapado; sin esos documentos, las salidas de P2 DEBERÁN quedar idénticas byte a byte. Criterios: P3.A12.

**Términos, documentación y recorrido real**

- **R17** — El repo DEBERÁ incluir, **antes** de los casos de uso que invocan agentes, `docs/agent-providers.md` §Términos, que registra con URL y fecha qué dicen los términos de Claude (Pro/Max) y de ChatGPT/Codex sobre invocación programática y la conclusión para Heron (D18, DR35); y al cerrar, el resto de `docs/agent-providers.md` (matriz de versiones, banderas exactas, política de entorno, configuración de roles), el ADR 0002 de zonas de escritura y el ADR 0005 de la frontera de proveedores de IA. Criterios: P3.A11.
- **R18** — El sistema DEBERÁ funcionar con Claude Code y Codex reales sobre `monorepo-fullstack`: el brief formula consultas por faceta de §8, cada dirección tiene los 13 atributos, cita ≥ 2 referencias y dice qué no copiar, y las notas del agente aparecen con origen `inferred`. Criterios: P3.A12.

**Economía de tokens (requisito del usuario, 2026-10-01: "no tope de costo no significa dejar abierta la manguera")**

- **R19** — CUANDO las entradas proyectadas, la plantilla, el schema, el proveedor y el modelo de una tarea sean idénticos a los del último run exitoso cuyo documento no fue editado, el sistema NO DEBERÁ invocar al agente ni escribir, y DEBERÁ informar el run reutilizado (`AGENT_RUN_REUSED`), salvo que el usuario pase `--force`; `research analyze` DEBERÁ enviar solo las referencias cuya clave de entrada cambió. Criterios: P3.A5.
- **R20** — CUANDO el sistema invoque a un agente, DEBERÁ enviar solo los campos que la tarea proyecta, con topes deterministas de ítems y de texto por referencia, el HTML convertido a texto y sin imágenes; ordenar el prompt con el prefijo estático (plantilla, schema, hechos de la tarea) primero y sin marcas de tiempo ni ids de corrida; pedir solo salida estructurada acotada (máximo de tokens de salida por tarea donde el CLI lo soporte); reparar enviando solo la salida previa, los issues y los hechos mínimos de la tarea; y alimentar `direction propose` con el análisis guardado en lugar de las fuentes crudas. Criterios: P3.A4.
- **R21** — El sistema DEBERÁ registrar por invocación los tokens de entrada, salida y cacheados y el costo cuando el proveedor lo reporta, mostrar en `status` y `doctor` los totales del día y de la ventana de retención del log local, y CUANDO los tokens del día superen `agents.warnTokensPerDay` DEBERÁ emitir `AGENT_BUDGET_WARNING` sin bloquear ningún comando. Criterios: P3.A5.
